17:T276c,<h2>Bean 3,000개 중에 실제로 쓰는 건 10개, 그런데 왜 다 로딩할까</h2>
<p>서비스 규모가 커질수록 Bean 로딩 메커니즘의 특성상 기동 성능 저하가 발생할 수 있습니다. 최근 이 문제의 해법으로 GraalVM이 자주 거론됩니다. DevOn Boot는 아키텍처를 바꾸지 않고도 기동 속도를 개선할 수 있는 Bean 로딩 전략을 제시합니다.</p>
<h2>배치는 왜 이렇게 느려졌을까</h2>
<p>이 문제는 특히 배치 환경에서 두드러집니다. 금융권이나 대규모 SI 환경에서는 시스템에서 쓰는 모든 Job과 공통 라이브러리, 업무 공통 코드를 하나의 배치 애플리케이션에 묶어 배포하고, 실행 시점에 파라미터로 원하는 Job만 골라 실행하는 방식을 씁니다. 그러다 보니 오늘 밤 실행할 Job은 1~2개뿐인데도, 기동 시점에는 애플리케이션에 포함된 전체 Job과 공통 코드가 함께 로딩되면서 관련 없는 Bean까지 만들어집니다. Job 수는 계속 늘어나는데, 온라인 서비스가 24시간 상시 운영되는 추세라 배치에 안전하게 할당할 수 있는 시간대는 오히려 줄어들고 있습니다. 그 결과 기동 지연이 곧 전체 처리 시간 지연으로 이어집니다.</p>
<h2>배치는 특히, 필요한 Bean을 미리 선택할 수 없습니다</h2>
<p>온라인과 달리 배치는 어떤 Job이 실행될지 실행 전에는 알 수 없습니다. 오늘 무엇을 실행할지는 코드가 아니라 실행 시점에 넘기는 파라미터에만 담겨 있어서, 빌드 시점은 물론 기동 초기에도 알 수 없습니다. 그래서 배치의 기동 지연을 제대로 풀려면, 지연 초기화 메커니즘 자체가 이 실행 시점 파라미터를 들여다볼 수 있어야 합니다.</p>
<h2>GraalVM이 먼저 떠오르지만</h2>
<p>컴파일 시점에 애플리케이션을 통째로 분석해 리플렉션과 동적 프록시 사용을 최소화하기 때문에, GraalVM Native Image는 기동 시간 자체를 밀리초 단위로 줄여줍니다.</p>

<p>다만 도입 자체에도 진입장벽이 있습니다. 네이티브 이미지 빌드는 일반 JAR 빌드보다 훨씬 오래 걸리고, 일부 라이브러리는 별도의 리플렉션 설정 없이는 정상 동작하지 않습니다. 여기에 이미 돌아가고 있는 시스템이라면 부담은 더 커집니다. 리플렉션에 의존하는 코드가 많을수록, 빌드 파이프라인을 새로 구성해야 하는 부담이 클수록 전환 비용이 커집니다.</p>
<h2>답은 이미 Spring 안에 있었습니다</h2>
<p>신규 도입이든 기존 시스템 전환이든 부담이 크기는 마찬가지이기 때문에, DevOn Boot는 아키텍처를 바꾸는 대신 Spring이 표준으로 제공하는 확장 포인트를 그대로 사용합니다. Bean 등록을 스캔 단계에서 걸러내는 방법도 검토했지만, 이 경우 실행 시점 파라미터를 들여다볼 수 없어 앞서 말한 조건과 맞지 않았습니다. 반면 <code>BeanFactoryPostProcessor</code>는 모든 Bean 정의가 끝난 뒤 한 번에 후처리하면서 동시에 <code>Environment</code>(실행 시점 파라미터)에도 접근할 수 있어서, 이 조건을 그대로 만족합니다. 그리고 이 방식은 배치에만 머물지 않습니다. 온라인 애플리케이션에서도 인프라 Bean은 즉시, 업무 Bean은 지연해서 만드는 동일한 원리가 그대로 적용됩니다.</p>
<h2>실제로는 이렇게 동작합니다</h2>
<p>DevOn Boot는 이 원칙을 LiveScan이라는 기능으로 제공합니다. 기본은 전부 지연해서 만들고, 정말 필요한 Bean만 예외적으로 먼저 만듭니다. "먼저 만들어야 하는 Bean"으로 인정하는 기준은 네 가지뿐입니다. 프레임워크 인프라이거나, 명시적으로 즉시 생성하도록 선언되었거나, 특정 초기화 인터페이스를 구현했거나, 배치라면 지금 실행 중인 Job에 해당하는 경우입니다. 이 네 가지로 충분하지 않다면, <code>additional-filters</code> 설정으로 특정 어노테이션이나 타입, 정규식 조건을 기준 삼아 eager Bean을 직접 추가할 수 있습니다.</p>
<pre><code class="hljs language-yaml"><span class="hljs-attr">devon:</span>
  <span class="hljs-attr">livescan:</span>
    <span class="hljs-attr">additional-filters:</span>
      <span class="hljs-bullet">-</span> <span class="hljs-attr">type:</span> <span class="hljs-string">ANNOTATION</span>
        <span class="hljs-attr">expression:</span> <span class="hljs-string">com.example.annotation.EagerBean</span>
</code></pre>
<p>적용도 어렵지 않습니다. 온라인은 의존성만 추가하면 자동으로 동작하고, 배치는 Job 설정 클래스에 어노테이션 하나만 붙이면 됩니다.</p>
<p>업무 모듈이 수천 개 클래스 규모로 커지면, 컴포넌트 스캔 자체를 건너뛰고 실행할 Job과 그 의존 패키지만 골라 등록하는 확장 모드도 제공합니다. 이 모드를 쓰려면 애플리케이션 클래스에 두 가지를 함께 선언해야 합니다. <code>@ComponentScan</code>에서 <code>@BatchJob</code> 클래스를 제외하고, 그 대신 확장 모드를 활성화하는 어노테이션을 붙이는 것입니다. 둘 중 하나만 쓰면 오히려 문제가 생기는데, 제외만 하고 활성화를 안 하면 Job이 아예 등록되지 않고, 활성화만 하고 제외를 안 하면 원래 스캔이 그대로 살아있어 모드를 켠 의미가 없어집니다.</p>
<pre><code class="hljs language-java"><span class="hljs-meta">@EnableLiveScanExcludedMode</span>
<span class="hljs-meta">@SpringBootApplication</span>
<span class="hljs-meta">@ComponentScan(excludeFilters = @ComponentScan.Filter(
    type = FilterType.ANNOTATION, classes = BatchJob.class))</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">BatchApplication</span> { ... }
</code></pre>
<p>이렇게 설정해두면, 별도 선언 없이도 Job 설정 클래스가 참조하는 필드나 파라미터 타입을 따라가면서 관련 패키지를 자동으로 찾아줍니다.</p>
<pre><code class="hljs language-java"><span class="hljs-meta">@BatchJob</span>
<span class="hljs-meta">@Configuration</span>
<span class="hljs-keyword">public</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">MonthlyReportJobConfig</span> {

    <span class="hljs-meta">@Autowired</span>
    <span class="hljs-keyword">private</span> MonthlyReportService service;   <span class="hljs-comment">// 이 타입의 패키지를 자동으로 찾아 등록</span>

    <span class="hljs-meta">@Bean</span>
    <span class="hljs-keyword">public</span> Job <span class="hljs-title function_">monthlyReport</span><span class="hljs-params">(Step step1)</span> { ... }
}
</code></pre>
<p>이렇게 등록된 의존 Bean은 별도로 eager 설정을 하지 않아도, 오늘 실행할 Job이 직접 참조하는 만큼 생성 과정에서 자연스럽게 함께 만들어집니다.</p>
<p>이렇게 분류된 결과는 운영 중에도 별도 엔드포인트로 조회할 수 있어서, 배포 후에 "왜 이 Bean이 즉시 생성됐는지"를 바로 확인할 수 있습니다.</p>

<p>이 수치는 실제 운영 환경이 아니라 테스트 조건(Bean 500개, Bean당 초기화 10ms 가정)에서 측정한 결과입니다.</p>

<h2>적용 전 체크리스트</h2>
<ul>
<li>업무 모듈이 수백 개 클래스 이하라면 별도 설정 없이 기본 방식으로 충분한지 확인했는가</li>
<li>업무 모듈이 수천 개 규모이고 패키지가 Job 단위로 잘 나뉘어 있다면 확장 모드를 검토했는가</li>
<li>Quartz 등 런타임 파라미터로 판별되지 않는 실행 방식이 섞여 있다면 해당 Bean을 별도로 지정했는가</li>
<li>배포 전에 <code>/actuator/livescan</code>으로 eager Bean 목록과 이유를 확인했는가</li>
</ul>
<h2>마무리</h2>
<p>다만 모든 상황에 맞는 건 아닙니다. Quartz처럼 실행 대상을 <code>spring.batch.job.name</code>이 아닌 다른 방식으로 결정하는 스케줄러는 자동으로 판별되지 않아 별도 설정이 필요합니다. 기본 방식은 업무 모듈이 극단적으로 많은 환경에서는 스캔 비용 자체가 완전히 없어지지는 않는데, 이런 경우엔 앞서 설명한 확장 모드로 보완할 수 있습니다.</p>
